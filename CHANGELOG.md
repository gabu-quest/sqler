# Changelog

All notable changes to sqler are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/).

---

## [Unreleased]

### Security

- **A reference stored in a document is resolved only when it is well formed.** `{"_table": ..., "_id": ...}` found in a document was used to build a `SELECT` with the table name taken from the stored data. It is now resolved only when `_table` is a valid table name and `_id` is an integer that fits SQLite's 64-bit range; anything else is left as it is. A reference whose `_id` is a string or a float is no longer converted to an integer, and an `_id` too large for SQLite no longer raises `OverflowError` when the document is read.
- **Field and key names used in queries are escaped.** A name with a quote could end the SQL string that held its JSON path, in `F("...")` comparisons and in `any()` on nested arrays. Names are now carried as data. A name with a backslash, a NUL, or whitespace other than single spaces raises `InvalidFieldNameError`.
- **Names ending in a newline are rejected.** `validate_table_name`, `validate_field_name` and `validate_identifier` accepted `"users\n"`.
- **Model field paths, the search index and the integrity helpers check what they put into SQL.** A key in a model field path (`any()` and filters on related models) is carried as data; the key `a'` no longer matches the key `a`, and an empty key raises `InvalidFieldNameError`. `FTSIndex` checks its fields, `tokenizer` and `index_table` when they are assigned as well as in the constructor, checks the model's table name, and `snippet()` raises `TypeError` for a `max_tokens` that is not an integer. `find_referrers`, `validate_references`, `set_null_referrers`, `cascade_delete` and their async versions raise `InvalidTableNameError` for a table name that is not a plain identifier, before any SQL runs.
- **The promoted write methods check their names.** `upsert_document_promoted`, `upsert_with_version_promoted` and `insert_many_promoted`, sync and async, raise `InvalidTableNameError` or `InvalidIdentifierError` for a bad table or promoted field name before any SQL runs.
- **A stored reference is followed only in a field declared as a model.** A `{"_table", "_id"}` dict found anywhere in a document was followed when the row was loaded, also in a plain `dict`, `list` or `Any` field and at any depth. Someone who could write such a dict into a free-form field (a comment's metadata, say) got another table's row loaded into that field by `query().all()`, `first()` and `from_ids()`, and made `from_id()` raise `ValidationError`. A reference is now followed only in a field whose annotation names a model class (`author: User`, `Optional[User]`, `list[User]`, `dict[str, User]`), and only into a table of a class that field admits or a subclass of it. A reference anywhere else comes back as the dict it is, and no statement is sent for it. Every way of loading gives the same, sync and async.

### Fixed

- **A filter through a reference field names the tables the two classes store in.** `Player.ref("team").field("name") == "red"` took the related table from the field's name (`team` gave `teams`, or a registered table of that name) and the outer one from the class name plus `s`, so on a class with its own `__tablename__`, a related class named unlike the field (`home: Address`), a class bound with `set_db(db, table)` or a field named like another class's table, the filter raised `sqlite3.OperationalError: no such table` or searched the wrong table. The outer table is now the one the class stores in, and the related one the table of the class the field's annotation admits (`Team`, `Optional[Team]`, `"Team"`, each entry of `list[Team]` with `any()`), on `SQLerModel` and `AsyncSQLerModel` alike. A field that admits no model class (a plain `dict`, a key the class does not declare) keeps the table its name gives; a field that admits classes of two tables, which named neither, now raises `ValueError` naming the class and the field. A filter on classes with default table names sends the statement it sent before.
- **A model field can hold a plain dataclass.** `save()` of a model whose field held a dataclass instance (`home: Optional[Address]`, `Address` a `@dataclass`) raised `UnstorableValueError: Object of type Address is not JSON serializable (at home)` on every base. It is now stored as an object of its fields, each in its stored form (a `datetime` in it is its ISO text, a dataclass in it an object again), and loads as the dataclass the field declares, also inside `Optional`, `list`, `tuple` and the values of a `dict`; an export and an import carry it. A field `__init__` does not take loads as `__init__` makes it, on every base. A lite model is still stored as a reference. A model inside a dataclass value (`home=Address(owner=saved_owner)`), which was then stored as a reference that no load resolved and no delete rule saw, is refused with `UnstorableValueError: model Owner inside a dataclass value is not stored as a reference: make it a field of the model (at home.owner)`, also in a list, tuple, dict or dataclass inside it, and nothing is written. A field holding a plain `msgspec.Struct`, which raised `Object of type Address is not JSON serializable (at home)` on the msgspec base, is stored in the shape msgspec reads back (an object of its fields by their encoded names, with its tag when it has one, a list when it is `array_like`) and loads as the Struct the field declares on the msgspec and lite bases; an export and an import carry it.
- **`AsyncSQLerDB.execute_sql()` returns the rows `SQLerDB.execute_sql()` returns.** The async one read each row by position, as an `_id` then a document: `SELECT COUNT(*) AS n` gave `[{"_id": 3}]`, a `GROUP BY` of two columns kept only the first, as `_id`, `SELECT _id, json_extract(...) AS name` dropped the name, and a statement whose first column is text, or `SELECT data, _id`, raised `ValueError: invalid literal for int()`. Both now read each row by its column names, by one rule: with a `data` column, its document with `_id` set from an `_id` column; with `_id` alone, `{"_id": id}`; else a dict of every column by its name. A `data` column whose JSON is not an object, read together with an `_id` column, raises `TypeError` on both, where the async one gave `{"_id": id}`.
- **First saves of a safe model that start together all succeed.** Several tasks on one `AsyncSQLerDB`, or several `SQLerDB` or `AsyncSQLerDB` objects on one file (as several processes have), saving a safe model at once into a table that does not exist yet or lacks its `_version` column, failed with `sqlite3.OperationalError: duplicate column name: _version` for each writer but one (8 tasks on a new database, 20 runs: 13 to 20 of 160 saves failed, 57 to 58 of 160 once a plain model had made the table; 4 objects on a new file: 18 to 25 of 80 sync, 27 to 45 of 80 async). `ensure_table(..., versioned=True)` called at once failed the same way. The look at the table and the `ALTER TABLE ... ADD COLUMN "_version"` now run in one transaction that holds the write lock from its start, so a writer that comes second finds the column and adds nothing. The first versioned write on a table without the column runs that transaction, and on `AsyncSQLerDB` looks at the table once more, as `SQLerDB` already did; later writes send what they sent before.
- **A model given a database of the other kind raises `TypeError` before anything runs.** `save(db=async_db)` on a sync model returned the model with a coroutine as its `_id` and wrote nothing, and `await save(db=sync_db)` on an async model wrote the row and then raised `TypeError: object int can't be used in 'await' expression`. Every way a database reaches a model, on every base, sync and async (`save`, `delete`, `refresh`, `from_id`, `from_ids`, `save_many`, `first_or_create`, `add_index`, `ensure_index`, `validate_references`, `using`, `set_db`, `bind`), now refuses anything that is not a `SQLerDB` for a sync model or an `AsyncSQLerDB` for an async one (a subclass of either is taken), with a `TypeError` naming the class, the type given and the database it takes; no statement runs and the instance and the class are left as they were.
- **A loaded lite or msgspec model with `TimestampMixin`, `AuditMixin` or `FullMixin` saves again.** A load (`Model.from_id(...)`, a query, `refresh()`) gave the mixin's `created_at`, `updated_at` and `deleted_at` as the ISO strings they are stored as, so the next `save()` raised `TypeError: can only concatenate str (not "datetime.timedelta") to str`, on the lite bases sync and async and on the msgspec base. Every field of a lite model, and every field a mixin gives a msgspec model, now loads as the type it declares, as pydantic and msgspec already load theirs: a `datetime`, `date` or `time` from its ISO string, a `UUID`, a path, an `Enum` member, a `Decimal`, a `timedelta`, a `tuple`, `set` or `frozenset`, and the same inside a `list`, `tuple`, `set` or the values of a `dict`. `refresh()` gives what a load gives: on a msgspec model it left a `datetime` field as its string and did not reload the fields a mixin gives. A lite field typed `datetime` that was saved holding a string that is no ISO date still loads that string. A union of two or more types besides `None` loads as stored. Measured on one row: `from_id` of a lite model with `TimestampMixin` went from about 17.0 to 18.7 µs, of a msgspec one from 16.1 to 18.1 µs; a model with no such field is unchanged within the noise.
- **Every import works on the lite and msgspec bases.** `import_csv` and `import_csv_string` imported no row of a lite or msgspec model (each raised `AttributeError: 'Field' object has no attribute 'annotation'`); `import_json`, `import_jsonl`, their `_string` forms and `async_import_jsonl` gave a lite model its `datetime` fields as strings, and refused a msgspec model with a mixin (`TypeError: Unexpected keyword argument 'created_at'`). Each import now builds a lite or msgspec row as a load builds it, so rows exported from any base import into it with equal values. With `update_existing=True` the values set on an existing row are of their field's type too, which also lets a pydantic model with `TimestampMixin` be updated by an import (it raised the same `TypeError` as above).
- **An empty CSV cell is a missing value.** `import_csv` gave every empty cell `None`, which a pydantic field such as `count: int = 0` refused. An empty cell is now `None` in a field that can hold `None` and leaves any other field at its default (or, with `update_existing`, at its value).
- **The default in-memory database waits for a lock, like every other.** On `SQLerDB.in_memory()` and `SQLiteAdapter.in_memory()` (shared cache, the default) a write or read that met another thread's lock raised `sqlite3.OperationalError: database table is locked` at once: 100 `save()` calls from 10 threads lost 67 to 70 of them, where `in_memory(shared=False)` and a file database saved all 100. Such a statement, sync or async, now waits up to `timeout_ms` for the lock and goes through once it is released, run once; it raises "database table is locked" only after `timeout_ms`. `executescript()`, and `executemany()` given rows from an iterator, still raise at once.
- **A reference field whose class is named in quotes follows the right class when two modules have a class of that name.** With `item: Optional["Item"]` and `Item` imported only under `TYPE_CHECKING`, sqler took the name to mean the `Item` class registered last. A reference to a row of the other `Item` then read as `None`, and a delete of that row was not refused. A name the module does not have now means every model class of that name, those defined later too; the stored `_table` says which one a row belongs to. This is the lite bases, sync and async: pydantic and msgspec refuse a class whose quoted name their module does not have.
- **A dict in a model field with the keys `_table` and `_id` and other keys is stored whole.** `{"_table": "t", "_id": 1, "label": "x"}` in a field of type `dict` was stored as `{"_table": "t", "_id": 1}`, with no error, by `save()`, `save_many()`, a queryset `update()` and `save_partial()` on every base, sync and async. See "Changed" for the rule.
- **Every write of a row moves its version.** A safe model's `save()` is refused with `StaleVersionError` when the row changed after the instance read it. Only the safe class's own writes moved the version, so a plain class's `save()` or queryset `update()` on the same table, `db.query(table).update()`, `db.upsert_document()` and `db.bulk_upsert()` changed the row and left the version, and a safe `save()` of an instance read before them wrote its old values over them with no error. The version of a row is now the `_version` column of its table and nothing else: every statement sqler sends that changes a row of a table with the column moves it by one, whichever class or method sends it; an insert writes 0. See "Changed" for what this does to existing code and files.
- **An update through a query built from an adapter alone moves the version too.** `SQLerQuery(table, adapter)` and `AsyncSQLerQuery(table, adapter)` have no database object that knows the table, so `update()`, `update_one()` and `update_n()` first read the table's columns (one more statement, 11 to 19 µs measured) and move `_version` where the table has it. `update(_version=...)` on such a query is refused, and the rows `update_one()` and `update_n()` return carry `_version`.
- **`move_promoted(..., keep="document")` moves the version of each row whose read value it changes.** Where a promoted column and a leftover document key disagreed, the move changed what the next read gave and left the version, so an instance read before the move saved the old value back with no error. Rows whose value the move does not change keep their version, and so does every row under `keep="column"`.
- **Sync: a loop that writes while it reads gets each row once, as its statement saw it.** On a file or shared-cache database, `iter()`, `iter_dicts()`, `stream_jsonl()` or a raw `adapter.execute()` cursor could give rows twice, with values its own loop had written, when the loop saved (2,000 rows indexed on a field gave 6,000). Before the thread sends another statement on its connection, the cursor now reads the rows it has not returned and serves them from memory. A loop that sends nothing still streams. A write after a loop left part-read no longer fails with "database is locked" once another connection has committed. A rollback reads nothing: a cursor or iterator left part-read when its transaction or nested transaction is rolled back raises `sqlite3.OperationalError` at its next read.
- **`db.query(table)` follows a table whose layout another database object changed.** After another `SQLerDB` or `AsyncSQLerDB` on the same file promoted a field into a column, `db.query(table)` went on reading the old layout: `all_dicts()`, `iter_dicts()`, `first_dict()` and `paginate()` gave documents without the promoted field, and a filter on it matched nothing. It now reads through its database object, as a model's query set does.
- **`created_at` and `updated_at` are equal after the first save.** Since 1.2026.4.3 the first save set `updated_at` one microsecond after `created_at`. Every later save still gives a strictly later `updated_at`, now also when the clock has not advanced or has gone backwards, and when two saves follow each other within one clock tick. Applies to `TimestampMixin`, `AuditMixin` and `AsyncAuditMixin`. A stored `updated_at` that lies in the future is not pulled back: the next save is one microsecond after it.
- **Async adapter: a task that ends holding a pooled connection no longer keeps it.** A task cancelled between a statement and its commit (an outer `cancel()`, a `wait_for` timeout) used to end with its connection out of the pool and its write transaction open, so every other writer waited out the busy timeout and failed with "database is locked". When the last task using a connection ends without releasing it, the connection is now rolled back and returned to the pool, once. `close()` waits for any such rollback first.
- **Async adapter: a task created while its parent held a connection no longer returns that connection twice.** The child inherits the pin; the connection now goes back to the pool when the last task using it releases it or ends, and a child whose inherited pin was already returned takes a fresh connection instead of sharing one that is back in the pool.
- **Async adapter: a failed rollback no longer shrinks the pool.** If rolling back a reclaimed connection fails while the adapter is open, a warning is logged, that connection is closed and a fresh one is put in the pool.
- **Async adapter: `adapter.connection` is `None` for a task whose inherited connection was already returned.**
- **Async adapter: a statement that fails outside a transaction no longer keeps its pooled connection.** A syntax error, a constraint violation, a wrong parameter count, a failed commit or a failed `BEGIN` used to leave the task holding the connection, with any write it had started, until the task ended. The connection is now rolled back and returned before the error reaches the caller; this also rolls back earlier statements of the same task that were not yet committed on it. Inside a transaction the connection stays until the transaction ends, and ending it returns the connection whether the commit or rollback succeeds.
- **Async adapter: a cancelled statement returns its connection by itself.** A `wait_for` timeout or `task.cancel()` reaches the caller at once, also while the statement waits on a lock held by another connection. The connection goes back to the pool once SQLite has finished with it, and a cancelled write is rolled back. A commit or `executescript` that SQLite had already started when it was cancelled still completes.
- **Async adapter: `executemany` inside a transaction no longer commits it**, so a rollback removes its rows. Outside a transaction `executemany` and `executescript` commit and return the connection.
- **Async: a task that outlives the transaction it was started in is outside it.** Its writes are committed on a pooled connection, `in_transaction` is False, and `db.transaction()` begins a new transaction with `BEGIN IMMEDIATE`. Before, such a write was rolled back without an error and the pool stayed one connection short.
- **Async: a statement of one task waits while another task's nested transaction on the same connection is open**, so that task's rollback can no longer undo it. Statements go in the order they were asked, also one that had waited when a nested transaction was about to open on top of it; a wait longer than `acquire_timeout` raises `LockTimeoutError`.
- **Async: when the end of a nested transaction fails in SQLite, the whole transaction ends rolled back.** No `RELEASE` follows a failed `ROLLBACK TO`, which kept the rows it was to undo. The nested block, every later statement in that transaction (`execute`, `executemany`, a new nested transaction, also one that was waiting its turn, from any task), every later nested end and the block that ends the transaction raise `TransactionStateError` with SQLite's error as its cause, and send nothing. A block that is already raising keeps its exception and gets the sentence as a note.
- **Sync: when the end of a nested transaction fails in SQLite, the whole transaction ends rolled back**, as on the async adapter and with the same message. `end_transaction()` swallowed the error: a `RELEASE` followed the failed `ROLLBACK TO` and kept the rows it was to undo, nothing was raised, and the outer block committed them. Now the nested end raises `TransactionStateError` (SQLite's error is its cause), every later statement of the thread in that transaction raises it and sends nothing, and the transaction ends with `ROLLBACK` and raises it. A block that is already raising keeps its own exception, with the sentence added as a note.
- **Sync adapter: `timeout_ms` is the lock wait on every database.** On a file database it reached nothing: every connection waited five seconds whatever was given (`timeout_ms=200` waited 5.0 s). Every connection now gets it as SQLite's `busy_timeout`, and `SQLiteAdapter.on_disk()`, `SQLiteAdapter.in_memory()`, `SQLerDB.on_disk()` and `SQLerDB.in_memory()` take `timeout_ms` (default 5000). A value that is not a whole number from 0 to 2**31 - 1 raises `ValueError`.
- **Async adapter: `timeout_ms` is the lock wait, under the sync adapter's rules.** `AsyncSQLiteAdapter`, its `on_disk()` and `in_memory()`, and `AsyncSQLerDB.on_disk()` and `in_memory()` take `timeout_ms` (default 5000 on the factories). Before, the wait could not be set: `on_disk()` sent a fixed `PRAGMA busy_timeout = 5000` and the other ways waited Python's five seconds. Every pooled connection gets the one number, a `busy_timeout` pragma sets it, a pragma that disagrees with it raises `ValueError` at `connect()`, and a value that is not a whole number of milliseconds raises at construction. `acquire_timeout` is still the wait for a connection of the pool; `timeout_ms` is the wait for another connection's lock.
- **Async adapter: `connect()` opens its pool once.** Called on a connected adapter, or at the same time as another `connect()` or a statement's own connect, it opened a second set of connections, failed with `QueueFull`, and left them running where `close()` never closed them. It now returns at once on a connected adapter.
- **Async adapter: a `connect()` that fails or is cancelled leaves nothing open.** It closes every connection it had opened, also when one of those closes raises or the task is cancelled again meanwhile, and raises the error that made it fail; the adapter stays not connected. `close()` waits for a `connect()` that is under way, so the two called together leave the adapter as the later one says, and a `connect()` after `close()` opens the pool again.
- **Async: an exception leaving `async with db:` after a nested transaction's end failed carries the rolled-back note**, as it does leaving sync `with db:`. The end error was swallowed without a word. The note is added once when the exception leaves several blocks (sync and async; sync added it once per block).
- **Sync adapter: a `connect()` that fails leaves nothing open.** A pragma that failed left the adapter saying it was connected, with a connection open.
- **Async: a statement that has its turn when the adapter is closed raises `NotConnectedError`** and sends nothing.
- **Async `query().all()`, `first()`, `from_id()` and `refresh()` raise a database error met while a referenced row is read** (for example `database is locked`), as the sync bases do. They returned the parent with an empty model in place of the referenced row: no `_id`, every field at its default. A typed reference into a table that is not a table of documents raises SQLite's error in the same way, and on the async lite bases a `TypeError` raised by the referenced row's class reaches the caller from `from_id()` and `refresh()`, as on the sync lite bases.

- **`async_export_jsonl` and `async_import_jsonl` run.** They imported `aiofiles`, which sqler does not depend on, and the import called `afrom_id` and `asave`, which no model has. They now need no extra package, do their file work off the event loop thread, work with all four async model bases, and give the same file and the same result as `export_jsonl` and `import_jsonl`.
- **JSONL import ignores a `_version` key in the file**, sync and async. An export of a safe model carries it; a lite safe model could not import its own export, and an update wrote the file's version over the stored one.
- **Async migrations are atomic.** `AsyncMigrationRunner` runs each migration's `up()` (or `down()`) and its version row in one transaction, as the sync runner does. A migration that fails or is cancelled leaves the schema, the data and the recorded versions as they were.
- **The async migration runner, `async_health_check`, `async_get_stats`, `async_checkpoint` and `async_vacuum` return their pooled connection** when they finish or raise. Inside your own transaction they keep using its connection and do not end it.
- **`async_health_check` always returns a `HealthStatus`**, also when returning the connection fails (the status is then unhealthy and names the error).
- **A migration runner first used inside a transaction that is rolled back** creates its version table again on the next call.

- **Sync adapter: a statement that fails outside a transaction no longer keeps the lock.** Python's `sqlite3` opens a transaction before a write and left it open when the write failed, so the thread held the write lock until its next commit and other threads got "database is locked". The failed statement, or a failed commit, is now rolled back before the error reaches the caller; this also rolls back that thread's earlier uncommitted statements, a raw `BEGIN` included. Inside `db.transaction()` nothing changes.
- **Sync adapter: `in_transaction` and `auto_commit()` are per thread.** A transaction open on one thread no longer stops other threads from committing. A plain `:memory:` database has one connection for all threads; its transaction belongs to the thread that opened it (next entry).
- **Sync adapter: on a plain `":memory:"` database a transaction belongs to the thread that opened it** (`SQLiteAdapter(":memory:")`, `SQLerDB.in_memory(shared=False)`). Other threads' statements wait for it to end, at most `timeout_ms`, then raise `sqlite3.OperationalError: database is locked`; every waiting thread goes on when it ends. Before, a second thread's transaction joined the first as a savepoint, and whichever thread ended the outer level committed or rolled back the work of both. A thread that ends inside its transaction has it rolled back, and a thread interrupted (Ctrl-C) while it waits holds nothing.
- **Sync adapter: on a plain `":memory:"` database a cursor no longer returns another thread's uncommitted rows.** A statement's rows are read before another thread may use the connection, so `query().iter()`, `iter_dicts()` and `stream_jsonl()` hold the whole result in memory there. A file database and a shared in-memory database are read as before.
- **`with adapter:` commits its own writes and leaves the thread's open transaction alone.** On a plain `":memory:"` database its writes (`bulk_upsert` uses it) stayed uncommitted on the one connection; inside a transaction of the same thread it committed that transaction early.
- **`backup()` and `restore()` on a plain `":memory:"` database wait for another thread's open transaction**, at most `timeout_ms`, and a `restore()` that runs out of time leaves that transaction as it is. They used to run in the middle of it.
- **`backup()` inside the calling thread's own open transaction fails at once**, on every database: the result is unsuccessful and says so, and nothing is copied. On a plain `":memory:"` database it never returned.
- **`upsert_with_version` and `upsert_with_version_promoted` end their `BEGIN IMMEDIATE`** when the update raises.
- **A safe save gives up on a locked database in bounded time.** A save that found the database locked was retried like a version conflict, up to 128 times with a full busy timeout each, and could wait for minutes. Lock waits now count against `RebaseConfig.lock_timeout` (5 seconds by default); past it the save raises `LockTimeoutError`. On a file database the longest wait is that limit plus one busy timeout. A lock met while the save re-reads the row after a conflict is handled the same way instead of leaving the save as `sqlite3.OperationalError`. Applies to all four safe model bases.
- **Sync adapter: `executemany` inside a transaction no longer commits it**, so a rollback removes its rows.

- **A model saved with `save(db=db)` and never bound with `set_db()` can be referenced and searched.** A model holding it stored a reference with no table, or raised "model must be bound"; its search index read the table `article` while the rows were in `articles`. Such a model is now stored as a reference, read back through `using(db)` with the related model in place, and found by `FTSIndex(Model, fields, db=db)`.
- **`first_or_create` under a unique index no longer fails when two callers race.** The caller whose insert is refused gets the other's row with `created` false. A refusal from a unique index on a field that is not in the lookup still raises `UniqueConstraintError`.
- **`save(db=db)` on a model with promoted columns creates its table** on a fresh database instead of raising "no such table" (sync bases).

- **A read of a missing table keeps your uncommitted work.** Both adapters rolled back the connection after any failed statement, so a raw statement left uncommitted outside a transaction was dropped when the same thread or task then read a table that does not exist. A read that fails with "no such table" now rolls back nothing; a failing write still does.
- **A table created in a transaction that rolled back is created again by the next write.** The database object kept remembering the promoted or versioned table, and the next write failed with "no such table". What it learns about a table inside a transaction now ends with that transaction: a commit keeps it, a rollback drops it, and neither sends a statement. This also holds for a transaction opened on the adapter directly (`db.adapter.begin_transaction()`), outside or inside `with db:`; nothing is remembered there, so the next write looks the table up again.
- **A safe model first saved inside a transaction that rolled back can be saved afterwards.** `SQLerSafeModel.save()` and `SQLerLiteSafeModel.save()` with promoted columns failed with "no column named ...".
- **A reference to a lite safe row loads after a rolled-back column promotion.** The loader selected the promoted column the rollback had removed.
- **Async adapter: a fetch that fails or is cancelled returns its connection.** `fetchone`, `fetchall`, `fetchmany` and `async for` on the cursor from `execute()`, outside a transaction. `execute()` now returns a wrapper around the `aiosqlite` cursor with the same methods and attributes; `isinstance(cursor, aiosqlite.Cursor)` is false.
- **Async adapter: a statement cancelled inside a transaction no longer holds the caller.** The cancellation reaches the caller at once instead of after the statement has finished in its thread; the connection returns to the pool, rolled back, when SQLite is done with it.
- **Ending a transaction by rollback raises nothing of its own.** The caller sees its own exception, also when the adapter was closed inside the block or the pool's only connection is still busy.
- **A failed `backup()` or `async_backup()` leaves the destination as it was.** The copy is made in a temporary file beside the destination and moved into place when complete; before, a failure left an empty or half-written file. A destination that is a symlink is written through, and an existing destination keeps its mode.
- **`metrics.disable()` puts the query logger back as it was before `enable()`.**
- **`metrics.prometheus_export()` gives valid output.** Label values and table names are escaped, and the duration histogram is declared once under `sqler_query_duration_ms` with `_bucket`, `_sum` and `_count` samples.
- **Two migration runners started together no longer report a failure.** The slower runner skips a version the other already recorded (`migrate`) or already removed (`rollback`) and reports success with nothing applied; each `up()` and `down()` runs once. Sync and async.
- **CSV export and import return every string unchanged.** The empty string, strings starting with `=`, `+`, `-`, `@`, tab or CR, and cells with line breaks round-trip. Export puts one apostrophe in front of such a string and import removes it; a cell such as `'90s` written by another program is read as written.
- **`import_csv(batch_size=N)` works.** An import that fails at a row keeps the full batches before it and nothing of the failed batch.
- **`AuditLogMixin` and `AsyncAuditLogMixin` write a change and its audit row together.** Outside a transaction a save or delete whose audit row is refused leaves no saved change, and a refused delete leaves no audit row. After a failed save the instance keeps its earlier `_id` and `_version`.
- **A safe model reached through a reference keeps its stored version**, so saving it does not raise `StaleVersionError` (never released; found while batching `from_id`).
- **A typed reference to a row that is gone reads as `None`, on every way of loading.** A field typed as a model (`Child`, `Optional[Child]`, `list[Child]`, `dict[str, Child]`) whose reference leads to no row of the field's class (the row deleted, its table dropped, a table of another class or of none, an unusable `_table` or `_id`) reads as `None` when it is the field's value and is left out of a list or a dict (the key goes too); in a tuple with one entry per place (`tuple[Child, Child]`) the entry reads as `None` at its place. That holds for `from_id`, `from_ids`, `refresh`, `query().all()` and `first()`, sync and async, on every model base. Before, depending on the way and the base, it gave a model of the field's class with every field at its default and no row behind it (saving its parent raised), the reference dict, `None` inside a list, or a `ValidationError`. A model loaded that way is dirty (`is_dirty()`), so `save()` writes what was read; a required field gets its class's own `ValidationError` on the pydantic bases.
- **A reference is followed only as deep as the field's annotation puts a model.** The field's value for `Child`, `Optional[Child]` and `Union[..., Child]`, an entry for `list[Child]`, a value for `dict[str, Child]`, nested as the annotation nests. A `{"_table", "_id"}` dict deeper than that is data, and nothing is read for it. A name the module gives to an annotation (`Children = list[Child]`, a `type` statement) is read through, in a quoted annotation too.
- **`from_ids` and `query().all()` no longer raise "no such table" when a referenced table is gone.** The reference reads as `None`, as `from_id` gives.
- **A lite safe model reached through a reference no longer recreates a dropped table.** The reference reads as `None`.
- **`set_db()` on the safe model classes reports its deprecation warning at your own line**, so Python's default warning filters show it.
- **`from_ids()` on a model with promoted columns gives the stored values.** The promoted fields came back at their defaults, and a `save()` of such an instance wrote those defaults over the stored columns. `find_documents`, sync and async, now returns promoted columns as `find_document` does.
- **A referenced row loaded through `from_ids()`, `query().all()` or `first()` carries its promoted columns.**
- **`from_ids()` on the safe model bases holds the stored `_version`.** It held 0, so saving a row that had been updated before raised `StaleVersionError`.
- **A database object that did not create a table reads its promoted columns.** A second process, `Model.using(db)` without `set_db()`, or any `SQLerDB` that never created or ensured the table read every row without them, through `find_document` as well. The columns are now read from the table, once per database object.
- **`resolve(False)` stays in force across chained calls** such as `resolve(False).filter(...)`, and a chained queryset keeps the database it was made from.
- **A very long id list no longer fails with "too many SQL variables"** in `from_ids()` and `find_documents()`.
- **A model loaded through `from_ids()`, `query().all()` or `first()` can be saved when it holds a typed reference.** A field typed as a model (`Child`, `Optional[Child]`, `list[Child]`) held a child without an `_id`, and `save()` raised "Related model must be saved before saving parent". The child is now the model of its row and can be saved itself.
- **Lite models: a typed list loaded through `from_ids()`, `query().all()` or `first()` holds models.** It held dicts, and `save()` replaced the stored references with copies of the rows.
- **A child of a safe model class loaded through `from_ids()`, `query().all()` or `first()` holds the version of its row**, so saving it no longer raises `StaleVersionError`.
- **`SQLerSafeModel.from_id()` and `refresh()` follow typed references**, sync and async. They gave an empty child without an `_id`.
- **`is_dirty()` is False for a model nobody changed, on every way it is loaded or saved.** It was True for a `SQLerModel` after `save()`, `save_many()`, `from_id()` and `from_ids()`, for a `SQLerSafeModel` after `from_ids()`, and on every model base as soon as a typed reference field was set. `get_dirty_fields()` names the fields `save()` would write differently, and no others.
- **`is_dirty()` sees a list or dict edited in place** (`model.tags.append(...)`, `model.meta["k"] = ...`) on the lite model bases, where it answered False. `save()` always wrote the edit.
- **`is_dirty()` does not raise for a model that holds a related model never saved**; every field is dirty.
- **A safe save that is rebased onto a newer row keeps the other writer's changes.** When a save on a stale version qualified for rebasing (by default a step of 1 on a field named `count`), every field of the saving model was written over the newer row, so a field only the other writer had changed went back to its old value without an error. The rebased save now writes the newer row, the fields the caller changed and the counter step.
- **After a rebased save the model holds what was written**, typed references included, and `is_dirty()` is False. It kept its values from before the merge, so a second `save()` wrote them back or raised `StaleVersionError`, and writers adding to one counter in turn lost increments.
- **A rebased save raises `StaleVersionError` when both writers changed one field to different values.** The saving model's value was written over the other writer's without an error. Nothing is written and the model keeps its values and its version; a field both set to the same value, and a counter both stepped, are merged as before.
- **A pydantic model with `extra="forbid"` reads its rows.** It saved, and every read (`from_id`, `from_ids`, a query, `refresh()`, a typed reference to it) raised `ValidationError`: the row's own `_id`, and `_version` on a safe model, were given to the class as fields. They are set on the model after it is built; a key of the row the class has no field for is still refused.
- **`cached_query(cache=...)` and `async_cached_query(cache=...)` use the cache they are given.** A cache with no entries counted as no cache, so the results went to the global cache and the given one stayed empty for good.
- **A call of a cached function that has to run counts as a miss.** Only `get()` counted misses, so `cache.stats.hit_rate` of a cache used through the decorators read 1.0 after its first hit.
- **A program that ends with an async database still open ends.** A script that raised, returned or called `sys.exit()` before `await db.close()` never exited: each connection runs a thread, and Python waited for it. The thread no longer holds the process. What was committed is kept; closing the database is still the way to end cleanly.
- **A value is stored in one form, whichever call writes it, and a filter binds that form.** A `datetime`, `date` or `time` is its `isoformat()`; a `UUID` or a path its `str`; an `Enum` its value; a set a sorted list; a tuple a list; a nested pydantic model its fields; the same at every depth of a list or dict. This holds for `save()` and `save_many()` of every model base, for `update()`, `update_one()` and `update_n()` on a query, for the document writes of `SQLerDB` and `AsyncSQLerDB`, and for the value in `F("field") == value` and the other comparisons. What it fixes:
  - `save()` raised `TypeError` for a field holding a `UUID`, a `time`, an `Enum`, a path, a set, or a nested model with a `date` in it, on every model base, and for a `date` on `AsyncSQLerModel` and `AsyncSQLerSafeModel`.
  - `F("happened") == datetime(...)` found no row: the filter bound `2026-11-14 09:30:00`, the row holds `2026-11-14T09:30:00`. `update(happened=datetime(...))` stored the form with the space.
  - `update(tags=[...])` and `update(meta={...})` stored a string of JSON text instead of a list or an object; a pydantic model could not load the row afterwards, and `contains()` found nothing in it.
  - `update(flag=True)` stored the integer 1 where `save()` stores `true`.
  - `is_dirty()` was True straight after loading a model with a tuple field.
- **A model with `AuditLogMixin` or `AsyncAuditLogMixin` can hold a `datetime`, a `date` or a reference.** Creating one with a `date` or a reference field raised `TypeError`, and so did updating one with a `datetime` field, `TimestampMixin`'s included. The audit row now compares the row before the save with the document the save wrote, so `changes` names the fields that changed and no others, and `changes` and `snapshot` hold values as they are stored: a datetime as its ISO text, a reference as `{"_table", "_id"}`.
- **A search index follows its table.** With `content_sync=True` (the default) `FTSIndex.create()` adds triggers that keep the index equal to its table whoever writes, and indexes the rows already in the table; the flag used to do nothing, so a row written without the mixin was not found and a changed row was found by its old words. An index made by an earlier version gets its triggers and its missing rows on the first `create()` after the upgrade, which reads the whole table once. A `create()` that finds the index as defined writes nothing and waits for no lock; one that fails leaves the index and its triggers as they were. An update that changes no indexed field does not rewrite the index. `content_sync=False` keeps the manual `index()`.
- **A search string that SQLite refuses raises `SearchQueryError`** naming the query, in place of a bare `sqlite3.OperationalError` (`C++`, `it's`, `foo-bar`, an empty string).
- **The FastAPI example runs again, on the public API.** Its seed wrote through `execute_sql`, which takes only reads, so seeding raised; its filters on a related row used `F("country._id")`, which is one key, so they matched nothing. It now names its database on every call (`Model.using(db)`, `save(db=)`, `from_ids(db=)`) and uses neither `set_db()` nor the adapter. Its tests run with the default `pytest` run, on a temporary database.
- **`FTSIndex` given an `AsyncSQLerDB` raises `TypeError`** saying the async database has no search yet, instead of an unrelated error later.
- **`query_logger.capture()` gives the statements of its block when the log is full.** The log keeps its newest 1000 entries, and a block opened on a full log got nothing (with 995 entries, a block of ten statements got five). A block now gets every statement logged while it is open, and its list fills as they are logged. Of two blocks that overlap, the one that ends first no longer switches logging off under the other; `enable()` and `disable()` called inside a block keep what they set once it ends; and `metrics.enable()` called inside a block keeps counting after it.
- **Sync adapter: a thread that ends gives back its connection.** Each thread's connection stayed open until `close()`, so a program that starts threads over its life grew one open connection per thread, and a thread that ended inside a transaction kept the write lock. The connection now closes when its thread ends, and its open transaction is rolled back. A shared in-memory database (`SQLerDB.in_memory()`) still lives from `connect()` until `close()`, whichever threads end in between.
- **Sync adapter: a thread that was running across `close()` and `connect()` works again.** It kept its closed connection and failed with "Cannot operate on a closed database."
- **`save_partial()` writes what `save()` would write for the changed fields.** It was a second write path beside `save()`. It raised `TypeError` on a `datetime`, a `Decimal`, a `timedelta` or a reference. A change to a promoted field went into the document and left the column, so every read gave the old value. On a safe model it skipped the version check and wrote over a newer row. On a row that was gone it wrote nothing and raised nothing. It ignored `db=` and `using()`, and timestamps, the audit log, cache invalidation and the search index did not run. It now goes through the model's own `save()`, which sends one `UPDATE` with the changed fields: a row that is gone raises `NotFoundError`; a stale one raises `StaleVersionError`, or is rebased where the model allows it; a model never saved is saved in full; with nothing changed no statement is sent. A key of the row that the model has no field for is left as it is, where a full `save()` drops it.
- **`TrackedModel` tracks changes on the lite bases.** `is_dirty` was always False there, so `save_partial()` did nothing, without an error.
- **Async: a cursor returns only what its statement saw.** A cursor from `AsyncSQLiteAdapter.execute` reads its rows as they are fetched. When its connection went on to another task before they were read (back to the pool after its transaction ended or after `auto_commit()`, to a sibling task in a shared transaction, to the rollback that ends a transaction), the read saw that task's work: a `SELECT` over 2000 committed rows returned another task's uncommitted rows as well, or rows it had since changed or deleted. Now the rows a cursor has not returned are read before another task's statement is sent on its connection, and served from memory. A cursor read by its own task reads lazily as before, and a cursor nobody holds any more is not read. If the connection is closed before the rows could be read, a read raises `NotConnectedError`; `docs/API.md` ("Async cursors") has the whole rule.
- **Async: two statements sent at the same moment on one shared connection are each answered whole.** With tasks sharing a transaction or a pinned connection, a `SELECT` sent in the same loop step as a sibling's write could return part of that write (4000 rows of 2000, or one row from before an update and the rest from after). The statement handed to the connection first is now answered as if the other had not been sent.
- **A frozen class read by a queryset reads clean.** A frozen lite or msgspec model returned by `all()`, `first()`, `iter()`, `update_one()` or `update_n()` came back with no snapshot (so `is_dirty()` was True for a row just read), because the queryset set that state by plain assignment and passed over the refusal. A lite class declared `@dataclass(frozen=True, slots=True)` failed `from_id` and `all()` with `TypeError: super(type, obj): obj must be an instance or subtype of type`; it loads now.
- **Promoting a field on a table that has rows moves each row's value from its document into the new column**, in one transaction, stored as `save()` stores it. Before, the column was added and the values stayed in the documents, where no read saw them: a pydantic row raised `ValidationError`, a lite row read `None`, a filter on the field found nothing, and a row promoted as `NOT NULL DEFAULT 'x'` that was loaded and saved lost its stored value with no error. A row without the key gets what it read before (the field's default, else the column's `DEFAULT`). A value the column cannot keep, or `NOT NULL` with no `DEFAULT` on an existing table, raises `SchemaError` and changes nothing.
- **A table whose promoted columns an earlier version left with values in the documents raises instead of reading wrong values.** It is checked once per database object, at its first ensure or its first read (`find_document`, `find_documents`, `from_id`, `from_ids`, every queryset method, the searches; sync and async), and raises `SchemaError` naming the columns and rows. Settle it with the new `db.move_promoted(table, column, keep="document")` (the document's value goes into the column) or `keep="column"`.
- **A `content_sync` search index made before a field was promoted keeps finding rows by that field**: the promotion remakes its triggers and refills it, in the same transaction.
- **`search_ranked()` gives the models `search()` gives.** It built its hits from the stored document alone: a promoted field read as its default, and a hit had no row version and no change tracking. It now reads ids and scores from the index and loads the rows by id (two statements where it sent one).
- **`save_many()` meets the rules of its class, as `save()` does**, on every base, sync and async. `TimestampMixin` and `AuditMixin` set the times and users on each row, `AuditLogMixin` writes one `create` audit row per instance in one unit with the batch, and `HooksMixin` calls `before_save()` on every instance before anything is written and `after_save()` on each once the batch is written. Before, a batch was written with none of them.
- **`delete_with_policy()` called directly writes the `delete` audit row and calls `before_delete()` / `after_delete()`**, as `delete()` does.
- **A delete with `on_delete="set_null"` or `"cascade"` is one unit with what it does to the rows that refer to it.** A refused delete leaves those rows as they were. Sync `set_null` no longer commits the caller's open transaction half way.
- **A write with an audit log that fails half way keeps nothing.** The row and its audit row are one unit: a transaction of its own, or a savepoint inside yours. Before, a row saved inside your transaction whose audit row failed stayed in it with no audit row, and was committed if you caught the error. The instance keeps the `_id`, snapshot and `_version` it had before the call, so the write can be made again.
- **A queryset's `update()` on a safe (versioned) model moves `_version`**, as `update_one()` and `update_n()` do. Before, a `save()` of an instance loaded before the `update()` was accepted and wrote its old values over the update; it now raises `StaleVersionError`.
- **A queryset's `update()`, `update_one()`, `update_n()` and `delete_all()` meet the rules of the class, as `save()` and `delete()` do**, sync and async. `TimestampMixin` and `AuditMixin` set `updated_at` (and `updated_by`) on each row in the same statement, at one time for all rows of the statement; a field you name in the update is kept. `AuditLogMixin` writes one `update` or `delete` audit row per row changed, in one unit with the write. Before, a set-based write did none of this. It still calls no hook: use a loop of `save()` where a hook must run. A class with no such mixin sends the statement it sent before.
- **A sync queryset write inside `db.transaction()` follows that transaction.** `update()`, `update_one()`, `update_n()` and `delete_all()` committed the caller's open transaction in the middle of its block, so a rollback afterwards kept the write. The async ones did not.
- **The rows a delete's policy changes meet the rules of their own class.** A row that `on_delete="set_null"` nulls gets its `updated_at` and its `update` audit row, and a row that `"cascade"` deletes its `delete` audit row. A nulled row of a safe (versioned) model moves its `_version`: before, a holder who had loaded the row could save the reference to the deleted row back with no error.
- **A transaction whose `ROLLBACK` failed is never joined by a later write (sync adapter).** When the `ROLLBACK` that ends a transaction failed in SQLite (an interrupt or a progress handler stopped it), after a block, a failed commit or a failed statement, or when a thread ended holding the `":memory:"` connection, the error was dropped and the transaction stayed open: the next write ran inside it and committed the rows that were to be rolled back. The rollback is now tried once more at once. If that fails too, or a `KeyboardInterrupt` arrives between the two tries, a thread's own connection is closed (which rolls back) with a warning and replaced at its next statement; the one connection of a plain `":memory:"` database keeps the transaction, the end raises `TransactionStateError` with SQLite's error as `__cause__`, and every later statement tries the rollback again first. See "A rollback that fails" in `docs/API.md`.
- **A document written through the database object lands where a read takes it.** On a table with a column beside `data` (a promoted field), `insert_document`, `upsert_document`, `insert_many`, `insert_many_with_version`, `bulk_upsert` and `upsert_with_version` of `SQLerDB` and `AsyncSQLerDB` put the whole document into `data`, where no read looks once a column exists: an update kept reading the old value and an insert read `None`. A write now puts each key the document holds into its column and touches no other column: an update leaves a column the document does not name, an insert leaves it to the column's `DEFAULT`, and a key held as `None` writes NULL. A model class without `__promoted__` therefore keeps a column it has no field for. See "Promoted columns" in `docs/STORAGE.md`.
- **`save_partial()` of a field that names a column beside `data` writes the column**, not a key in `data`.
- **`bulk_upsert` on a table with more columns than one statement can bind** writes one row per statement instead of raising `ValueError`.
- **Sync adapter: on a plain `":memory:"` database an exception around a statement no longer locks other threads out.** An exception that reached a thread around one of its statements (a signal, a trace function, an exception set from another thread) could skip the bookkeeping that hands the shared connection on: every other thread then got "database is locked" until `close()`. A thread that ends while holding an open transaction has it rolled back even when that bookkeeping was skipped, a thread that was already waiting goes on when its wait runs out, and a new thread that reuses the dead thread's ident joins nothing it left.
- **Sync adapter: on a plain `":memory:"` database a versioned update refused outside a transaction raises its own error at once.** It waited behind another thread's transaction and then raised "database is locked" in its place.
- **Sync adapter: an exception at any point of an outermost `end_transaction` leaves no transaction that a later statement of the thread joins.**
- **A safe (versioned) model never changes a table on a read.** `from_id`, `from_ids`, `refresh`, a followed reference, `query()` and `using(db)` read a table made without a `_version` column with each row at version 0, also on a database opened read-only, and a read of a missing table creates nothing. The first versioned write of such a table (a save, or a set-based update) adds the column. Before, a by-id read of a safe model added the column, which fails on a database that cannot be written. A versioned query asks for the column once per database object and table and sends no extra statement after that; `count()`, `exists()` and the aggregates never ask.
- **`copy.copy` and `copy.deepcopy` of a lite model declared `@dataclass(frozen=True, slots=True)` keep its `_id` and snapshot**, as on the other lite models. The copy had no `_id`, so its `save()` inserted a second row.
- **Search: with a hand-made index (`content_sync=False`) the mixin's `save()` and `delete()` keep the entry in the database the row is written to.** Deleting a row that lives in another database (read with `Model.using(other)`, or saved with `save(db=other)`) removed the entry of the same id in the index's database, so a search missed a row that was still in the table. The entry is now written through the row's database, inside its transaction; a row of another table and a database without the index table touch no index. The default index (`content_sync`) was not affected.
- **Async adapter: an `async with db.adapter:` block inside a transaction no longer ends that transaction.** A block that ended normally committed the first half of the transaction; a block whose exception was caught rolled back the rows written before it while the transaction went on and committed the rest, with no error. The block now leaves the transaction to its owner, as the sync `with db.adapter:` block does.
- **A sync `MigrationRunner` made inside a transaction no longer commits that transaction** while it makes its tracking table; the table belongs to the transaction, as with `AsyncMigrationRunner`.
- **A delete's look for referring rows no longer rolls back raw work that was pending before it.** On a table with a row SQLite's JSON functions cannot read, the look's first read fails and it reads another way; that failed read used to roll back whatever was uncommitted on the connection, with no error.
- **Async: a statement of a transaction that was cancelled after its connection had closed no longer makes every later statement of that transaction wait forever.** The next statement raises `ValueError` ("no active connection") at once.
- **Async: a read of a cursor's rows that ends the transaction is seen even when another task's statement ran behind it.** The read raises `TransactionStateError` and the transaction ends rolled back; before, later statements could go out in a transaction SQLite had opened anew, and the block's `COMMIT` kept them after the earlier writes were gone. A cancelled read and a failed read-ahead are covered too. It takes a function in the statement that rolls back its own connection to reach this.
- **A database object follows a table that another connection changed.** A `SQLerDB` or `AsyncSQLerDB` remembers the columns of each table it has used. When another object or process promoted a field, added `_version`, or dropped and remade the table, the first one went on by what it remembered: a write put the promoted field into the document, where no reader of the new layout looks, a read by id came back without the new column, and nothing was raised. Every statement built from that memory now names the columns it was built for. SQLite refuses it once the table has others; the object then reads the table again, builds the statement again and sends it. The caller sees no error, no field is lost, and work left uncommitted before the statement is kept.
- **A write puts every key that names a column of the table into that column**, also a column that another class or database object promoted (model classes with `__promoted__`, and the `*_promoted` writers). Before, such a key went into `data` and the column read back NULL.
- **The triggers of a `content_sync` search index are built from the table as it is when `create()` runs**, so a row saved after another object promoted an indexed field is found by a search.
- **A delete with `on_delete="set_null"` writes the referring row as a save does.** A promoted stamp lands in its column, and on a table that was remade without `_version` it writes the row without one, where the delete raised `no such column: _version`.
- **`bulk_upsert` gives the caller's documents their new `_id` only when the whole call succeeded.** After a failure they are as they were passed; before, they kept the ids of rows that had been rolled back.
- **`AsyncSQLerDB.bulk_upsert` is one transaction, as the sync method is.** A failure half way writes nothing, where it left the rows before the failure written.
- **A write by `_id` creates no table.** `upsert_document` with an `_id` and a save of a loaded row raised `NotFoundError` on a database without the table and left an empty table behind; an update of some fields and an async plain model saved by `_id` made the table too. They create nothing now.
- **A cached query no longer returns rows that a committed write has replaced.** With `CacheAwareModel` on a class, a function cached with `cached_query(table=...)` could go on returning the old rows after a write until the entry's lifetime ended: a reader that ran between a writer's `save()` and its commit stored the old rows again, and only `save()` and `delete()` of an instance told the cache at all. Now every way of writing the class's rows drops the cached results of its table: `save()`, `save_partial()`, `save_many()`, `delete()`, `delete_with_policy()`, the rows a delete's policy nulls or deletes, and a queryset's `update()`, `update_one()`, `update_n()` and `delete_all()`, sync and async. While a transaction of this process that wrote the table is open (`db.transaction()`, `with db:`), no result of the table is served from the cache or stored in it, and a result is stored only if the table was not written while its function ran. The mixin sends no statement.
- **On an async model, `CacheAwareModel` tells the cache when the awaited write has run**, not when the coroutine is made.
- **`save_many()` leaves the change tracker of a `TrackedModel` or `AsyncTrackedModel` clean**, as a loop of `save()` does. The instances read dirty after it, with their history.
- **Async adapter: a statement a task sends on the connection of one of its own unread cursors reads that cursor's remaining rows first** (a `save()` inside a loop over the rows of `adapter.execute(...)`, a commit), so the cursor gives each row once, with the values its statement saw. Before, the rows were read lazily under the task's own writes and could come twice with changed values, or the write failed with "database is locked".
- **Async adapter: a cursor closed inside an `async for` over it gives no row after the close.** The next step raises `sqlite3.ProgrammingError`, and `NotConnectedError` when the adapter was closed. Before, the loop first gave the rest of the chunk it had fetched, up to 63 rows.

### Changed

- **A lite model loads each field as the type it declares.** A lite field typed `datetime`, `date`, `time`, `UUID`, `Path`, `Enum`, `Decimal`, `timedelta`, `tuple`, `set` or `frozenset` loaded as its stored form (a string or a list); it now loads as its type, as a pydantic or msgspec field does. Code that parsed the loaded string itself (`datetime.fromisoformat(row.created)`) now gets the value and must drop the parse. The fields a mixin gives a msgspec model follow the same rule.
- **A new row sends `CREATE TABLE IF NOT EXISTS` only until the database object remembers its table.** `insert_document`, `upsert_document` with no `_id`, and a model's `save()` of a new row sent it before every insert (a model twice), each with its own commit. A table dropped behind the object's back is made again by the next insert, as before. `from_id` and `from_ids` of a class with no model-typed field build their rows without starting the reference loader.
- **A stored reference is a dict of exactly two keys**, `_table` a `str` and `_id` an `int` that is not a `bool`. Any other dict is data: stored whole, read whole, not followed by a load, not counted as a referrer by a delete, and not reported by `validate_references()` or `find_ref_paths()`. `sqler.utils.is_ref_dict` is the one test. Every released sqler writes a reference as exactly those two keys, so stored references read as before. Code that wrote a dict with more keys, or with an `_id` that is a string, float or bool, and relied on it being followed will find it is data now.
- **A cursor returned by the sync `adapter.execute()` runs no other statement.** Its `execute()`, `executemany()` and `executescript()` raise `sqlite3.ProgrammingError`; send the next statement with the adapter. Sent from the cursor, a statement skipped the adapter's transaction handling, and would now skip the reading ahead that keeps rows as their statement saw them.
- **A delete's audit row holds the row as it was stored.** An instance edited and not saved before its `delete()` logs the stored values, not the edits. A `delete()` of a row that is already gone writes no audit row; it wrote one with the instance's values.
- **The version of a row lives only in its `_version` column.** The document holds no copy: a `_version` key in a document written to a table with the column is dropped, and every read through a database object or a model (`find_document`, `db.query(table)`, a model's query set, a model) gives `_version` from the column, so a plain read of such a table now has a `_version` key in each document. On a table without the column nothing changes: a `_version` key is your data, and the statements sent are the ones sent before. A file last written by 1.2026.4.4 is used as it is, with no migration step; a `_version` key that version left inside a document is dropped by the next write of the whole row. **1.2026.4.4 and this version cannot use one database file at the same time**: `docs/STORAGE.md` says which side fails with an error and which write is lost with none.
- **`_version` cannot be named in an update of a table that has the column**, through any query: `update(_version=...)`, `update_one` and `update_n` raise `ValueError`, because every update of a versioned row moves it. A safe model's query set refuses it before it touches the table. On a table without the column it stays a document field.
- **`with_version()` on a table without a `_version` column reads and writes with no version.** It raised SQLite's "no such column: _version". A query from a database object reads and moves the version wherever the table has the column, asked or not.
- **An async `delete()` of a row that other rows refer to is refused, as the sync one always was.** On `AsyncSQLerModel`, `AsyncSQLerSafeModel`, `AsyncSQLerLiteModel` and `AsyncSQLerLiteSafeModel`, `await obj.delete()` and `delete_with_policy()` (default `on_delete="restrict"`) now raise `ReferentialIntegrityError` and delete nothing. Before, they deleted the row and left the referring rows pointing at no row, with no error. Async code whose deletes went through will now get this error: delete or null the referrers first, or pass `on_delete="set_null"` or `"cascade"`. An async delete runs the same look for referring rows as a sync one.
- **The look for referring rows and the delete are one transaction**, on every base, sync and async (a savepoint inside yours), so another connection cannot write a referrer between the check and the delete. Before, a sync `restrict` delete of a class with no audit log could leave such a referrer pointing at no row. One effect: a `delete()` on a connection where a raw `db.adapter.execute()` write was left uncommitted now raises sqlite's `cannot start a transaction within a transaction`, as `set_null`, `cascade` and `db.transaction()` already did; commit the raw write first.
- **An async `delete_with_policy(on_delete="cascade")` of a row that refers to itself writes one `delete` audit row**, as sync does, not two.
- **`delete_all()` meets the delete policy.** On both query sets it takes `on_delete=` (`"restrict"`, the default; `"set_null"`; `"cascade"`), as `delete()` does. By default it now raises `ReferentialIntegrityError` and deletes nothing while a row outside the set refers to a row in it. Before, it ran no check: the rows were deleted and the referring rows kept references to no row, with no error. Code whose `delete_all()` went through may now get this error: delete or null the referrers first, or pass `on_delete="set_null"` or `"cascade"`. The DELETE, the look for referring rows, the policy and the audit rows are one unit. It returns the number of rows its own DELETE removed; rows a cascade deletes are not counted. A class no class can refer to, with no row rules, still sends its one DELETE.
- **Only a field declared as a model counts as a reference when a row is deleted.** A row refers to another when it holds the reference at a position its class declares as a model (`author: User | None`, `list[User]`, `dict[str, User]`, nested, or a base class of the target): the positions a load follows. A `{"_table", "_id"}` dict in a plain `dict`, `list` or `Any` field is data: it no longer refuses a delete under `restrict`, and it is no longer nulled or cascaded. Before, any such dict anywhere in a document counted. `validate_references()` still reports one whose row is gone, and `find_ref_paths()` is unchanged. The fields that count for a table are those of every class whose rows live in it (a subclass that inherits its table, another class bound to it, a class used there through `using(db, table)`). Only classes the program has defined are known: import the modules of the classes that refer to a table before deleting from it.
- **Rows deleted together are not referrers of each other.** A row that refers only to itself is deleted under `restrict` (it was refused), and a parent and its children deleted in one `delete_all()` go through.
- **The look for referring rows reads only the tables whose classes can refer to the row**, once per table for any number of rows; before, every delete scanned every registered table. A delete of a row of a class no class can refer to reads no other table. Beside 20,000 referring rows a delete takes about two thirds of the time it took (9 to 13 ms against 14 to 17, measured on one machine). On a large referring table, an index on the reference field (`db.create_index("posts", "author._id")`) turns the look into a search (0.2 ms). `find_referrers()` and `set_null_referrers()`, sync and async, take one id or a collection of ids. A row written by hand that SQLite's JSON functions cannot read (`NaN`, `Infinity`) is read as a load reads it, not passed over.
- **A model kept in an untyped field reads back as its reference.** This follows from the security entry "A stored reference is followed only in a field declared as a model". A model put into a `dict`, `list`, `Any` or unannotated field is still stored as a reference, and is now read back as `{"_table": ..., "_id": ...}`. To get the model back, declare the field: `author: Optional[User] = None`, `tags: list[Tag]`, `by_key: dict[str, User]`. The stored rows need no change. A model loaded with a reference dict in an untyped field is not dirty, and `save()` writes the row back unchanged. A class with no typed field sends no statement for references and walks no document when it is loaded.
- **The PyPI publish workflow runs the linter and the test suite first**, and refuses a tag that does not match the version in `pyproject.toml`.
- **Async adapter: `executescript` inside a transaction raises `QueryError`**, because SQLite commits the open transaction before it runs a script.
- **Async adapter: waiting for a pooled connection times out.** `acquire_timeout` (seconds, default 30, `None` waits forever) on `AsyncSQLiteAdapter`, `on_disk()` and `in_memory()`; a wait that runs out raises `ConnectionPoolExhaustedError`. Tasks waiting when `close()` is called raise `NotConnectedError`.
- **Async: a transaction, or a nested transaction, that commits while another task's nested transaction is still open inside it is rolled back.** The block and the other task both get the new `TransactionStateError` (a `ConcurrencyError`, exported from `sqler`). End the tasks inside the block: await them there, or use a `TaskGroup`. A nested transaction that is only still being closed is waited for and the commit goes through. A task that ends with its own nested transaction open has it rolled back.
- **Sync adapter: a `busy_timeout` pragma and `timeout_ms` are one number.** A `PRAGMA busy_timeout = N` in `pragmas` with no `timeout_ms` sets the adapter's `timeout_ms`, which on a plain `":memory:"` adapter is also the wait for another thread's transaction (that wait was five seconds whatever the pragma said). Given beside a `timeout_ms` that differs, `connect()` raises `ValueError` naming both.

- **`adapter.executescript()` inside an async migration fails.** The migration now runs in a transaction and the adapter refuses a script there. Use one `adapter.execute()` per statement; the failed `MigrationResult.error` says so.
- **`async_vacuum` inside a transaction raises `QueryError`** before it runs anything; the transaction stays usable.

- **Sync adapter: `executescript` inside a transaction raises `QueryError`**, as the async adapter does.
- **`SQLiteAdapter.execute()` is annotated as returning `CursorLike`** (`sqler.adapter.abstract`): `fetchone`, `fetchmany`, `fetchall`, iteration, `description`, `rowcount`, `lastrowid` and `close`. A `sqlite3.Cursor` is one, and so are the rows a plain `":memory:"` database has already read. Code that needs another attribute of `sqlite3.Cursor` (`connection`, `row_factory`) does not find it on those rows.
- **`RebaseConfig.max_retries` counts version conflicts only**, and a safe save sleeps at most 50 ms between two tries.
- **`FTSIndex.fields` returns a copy.** Appending to it no longer changes the index; assign a new list instead.
- **A violated unique index or primary key raises `UniqueConstraintError`**, sync and async, from every write path including a raw `adapter.execute`. It names the table and columns SQLite reported (or the index, for an index on an expression) and has the driver error as its cause. It is still a `sqlite3.IntegrityError`, so `except sqlite3.IntegrityError` keeps working; NOT NULL, CHECK and FOREIGN KEY errors are unchanged.

- **Every route uses one rule for a model's table**: the table bound with `set_db()`, else `__tablename__`, else the plural of the class name. For a class that was never bound, `FTSIndex` now reads `articles` instead of `article`, so its default index name changes from `article_fts` to `articles_fts`.
- **A read creates no table.** `find_document`, `find_documents`, `find_document_with_version` and `query()` of `SQLerDB` and `AsyncSQLerDB`, and through a model `query()`, `using(db)`, `from_id`, `from_ids` and `refresh`, give the empty answer on a table that does not exist (`[]`, `None`, 0, false; a queryset `update()` or `delete()` changes 0 rows) instead of creating the table or raising "no such table". A query built by hand (`SQLerQuery(table=..., adapter=...)`, `AsyncSQLerQuery(...)`) does the same, where it raised "no such table"; `explain()` and `explain_query_plan()` still raise. The exports (`export_csv`, `export_json`, `export_jsonl` and their string, stream and async forms) of a table that does not exist write what they write for an empty table. A read no longer needs the write lock. "no such table" for another table in the query still raises. `find_document_with_version` still adds a missing `_version` column to an existing table.
- **Model classes are registered when they are defined**, so `sqler.registry.tables()` lists classes that were never bound, and the integrity scans look at their tables. A class bound with `set_db()` is never replaced by a class that is only defined.
- **`as_ref()` on an unsaved model** now says "model must be saved"; a saved model no longer has to be bound.

- **`from_id()` and `refresh()` read each referenced table with one query** instead of one query per reference (a row with 20 references: 2 queries, was 21), and a cycle of references is cut at the first row seen again, as `from_ids()` cuts it, instead of after about 160 levels.
- **A reference that is kept as it is stored is left whole.** That is a reference to a row being loaded further up (a cycle) and one deeper than `max_depth`. `from_id()`, `refresh()` and async `query().all()` no longer load references nested inside it.
- **Async `query().all()` no longer walks each row twice.** It follows references in the batch only, as the sync bases do.
- **A rebased save raises `StaleVersionError` when the newer row cannot be loaded as the model class** (text where the class has a list, on the pydantic safe bases). The validation error is its cause; nothing is written. Before, the save went through and wrote the caller's old values.
- **Rows that `update()` wrote before this release keep the form they were written in.** A datetime written by `update()` has a space where `save()` writes `T`, and a list or dict written by `update()` is a string of JSON text; filters now bind the `save()` form and do not find the first, and the second was never a list. To rewrite them (table `events`, fields `happened` and `tags`):

  ```sql
  UPDATE events SET data = json_set(data, '$.happened', replace(json_extract(data, '$.happened'), ' ', 'T'))
  WHERE json_extract(data, '$.happened') LIKE '____-__-__ __:__:__%';

  UPDATE events SET data = json_set(data, '$.tags', json(json_extract(data, '$.tags')))
  WHERE json_type(data, '$.tags') = 'text' AND json_valid(json_extract(data, '$.tags'));
  ```

  The second statement also turns a field that is meant to hold a string of JSON text into the list or object; leave such a field out.
- **The audit log reports what changed in the stored row.** A key of the row that the model class has no field for is listed in `changes` with `new` null, because `save()` drops it. A save that stores nothing, because the row was deleted in the meantime, writes no audit row.
- **A `Decimal` is stored as a number.** `save()`, `update()`, the document writes and filters refused a `Decimal`. It is now stored as the JSON number it equals: an integer when it is whole (`Decimal("5.00")` is stored as `5`), else a float, and only when reading that float back gives the same `Decimal`. `Decimal("0.1")` is stored; `Decimal("0.1234567890123456789")`, `Decimal("1E+30")`, a whole value outside SQLite's 64-bit integers, `NaN` and `Infinity` are refused, so a stored value is never a rounded one. Store such a value as text (`str(value)`) in a `str` field. A filter by a `Decimal` finds the rows written with it, and a filter by a refused `Decimal` raises instead of finding nothing. A model base that decodes by annotation (pydantic, msgspec) loads the field as a `Decimal` again; the lite bases load the number.
- **A value with no stored form raises `UnstorableValueError`.** It is a `ValidationError` and still a `TypeError`, so `except TypeError` keeps working. `value` is the refused value; `field` is its place and the message names it: the path in the document for a document write (`lines[2].price`), the field and the path inside it for a model save (`v[1].price`), the column for a promoted column. `bytes` in a document are refused this way (see below).
- **A `timedelta` is stored as its number of seconds.** `save()`, `update()`, the document writes and filters refused a `timedelta`. It is now stored as a JSON number: an integer when the seconds are whole, else a float, and only when `timedelta(seconds=number)` equals it; a `timedelta` that no number of seconds holds raises `UnstorableValueError`. Filters, ordering, `sum()` and `avg()` work on the seconds. A model base that decodes by annotation (pydantic, msgspec) loads the field as a `timedelta` again; the lite bases load the number.
- **`bytes` in a document say where they go.** `bytes`, `bytearray` and `memoryview` in a JSON document raise `UnstorableValueError`, with a message that says to promote the field to a `BLOB` column or store text; `update()` raised `sqlite3.OperationalError` for them. A field promoted to a `BLOB` column takes them as they are.
- **`FTSIndex.create()` raises `SchemaError` when the index exists with another definition**: other fields, another field order or another tokenizer. It used to keep the old index without a word. Call `drop()` then `create()` to change an index. With `content_sync=False`, `create()` drops the index's triggers.
- **`is_dirty()` answers what `save()` would change in the stored row.** One case now reads dirty where it did not: a typed reference whose row is gone and reads `None`, because `save()` would write null over the reference.
- **One `NoAdapterError`.** The sync and the async query raise `sqler.NoAdapterError`. It is a `QueryError` and still a built-in `ConnectionError`, so `except ConnectionError` keeps working.
- **`F('')` raises `InvalidFieldNameError`.**
- **`FTSIndex` refuses a search field with a dot** (`meta.title`) with `InvalidIdentifierError` in the constructor and the `fields` setter; before, `create()` failed with an SQLite parse error.
- **`import_csv()`'s `batch_size` default is `None`** (one commit per row, as before); it was 100 and ignored. A value below 1 raises `ValueError`.
- **CSV import removes one leading apostrophe from a cell that looks escaped**: apostrophes followed by nothing or by `=`, `+`, `-`, `@`, tab or CR. Such a cell written by hand or by another program is read without that apostrophe.
- **`metrics.enable()` raises `ValueError`** for a custom label named `le`, `table` or `operation`, or for two labels that become the same name once cleaned.
- **A column added to a table by hand shows in documents read by id**, under the column's name, when that name is a valid field name.
- **Lite safe models: `from_ids()` sends one statement** instead of one per id, and leaves out an id given as a string, as `from_ids()` on the other bases does.
- **`SQLerSafeModel.from_id()` and `refresh()` raise `ValidationError` for a typed list that names a deleted row**, as `SQLerModel.from_id()` does. They gave an empty child in its place.
- **A `mode="before"` validator on a typed reference field receives the child model** through `from_ids()`, `query().all()` and `first()`, as it does through `from_id()`. It received the stored dict.
- **Async `query().all()` cuts a cycle of typed references where the other ways do**, one level earlier than before, with fewer statements.
- **`save_partial()` refuses a field name that holds a double quote or a backslash** with `InvalidFieldNameError`, before any statement: no JSON path names such a key on every supported SQLite. `save()` stores such a field as before.
- **`save()` on every model base and mixin takes a private `_partial` keyword.** A class that overrides `save()` and is used with `save_partial()` must accept `**kwargs` and pass them on.
- **Async: `connect()` raises `sqler.ConnectionError` when the installed `aiosqlite` lacks an internal the adapter uses**, naming `aiosqlite`, its version and what is missing, instead of failing at the first statement.
- **A typed reference loads as the model of its row by every way of loading** (`from_id`, `refresh`, `from_ids`, `query().all()`, `first()`, sync and async) on every model base, msgspec included. Before, `from_id` read one row per `SELECT` and stopped partway down a long chain, the other ways stopped after 6 models, and where they stopped the pydantic bases built a blank model from the stored reference (or raised `ValidationError` for the whole load when the class has a required field). Chains are now followed to their end with no depth limit, with one `SELECT` per table per level; there is one object per row per load, and a cycle closes on its objects (`a.next.next is a`). A row in a cycle holds every field of its row whatever way its class keeps its state (`slots=True`, frozen, private attributes), and a hook that keeps `self` keeps the object the graph holds. A msgspec `__post_init__` runs once for each row, on the row's values (see `docs/API.md`).
- **With `.resolve(False)` and `iter()`, a typed reference field holds the stored `{"_table", "_id"}` reference on every base**, never a model built from it, also when the child class has required fields; saving writes it back unchanged.
- **A referenced row its class refuses raises the exception that loading that row by its own `from_id` raises** (`msgspec.ValidationError` on msgspec), with a note naming the row, its table and the referring field. Before, the answer depended on the base and the way of loading: a blank child, the stored reference or the class's error.
- **`repr()` of a pydantic model in a cycle prints the model met again as `...`** instead of raising `RecursionError`; lite `model_dump()` of a cycle raises `ValueError`, as pydantic's does.
- **An ensure on a table that needs no change no longer fails when another connection holds the write lock or the database is read-only**; what it would have recorded is written by a later ensure.
- **An error from the end of a transaction is named on the exception that was leaving.** When a block's own exception leaves and ending the transaction raises something other than `TransactionStateError`, the block's exception now carries the note "ending the transaction failed: <Type>: <message>", once; the error was dropped. A failed outermost `ROLLBACK` is still handled inside the adapters and does not reach this note.
- **`before_save()` runs before the timestamps are set**, so a `before_save()` that returns False leaves the instance unchanged. `delete()` of an instance that was never saved raises `ValueError` before `before_delete()` is called.
- **The async models have `save_many()`.** `asave_many()` still works, warns with `DeprecationWarning` and calls it.
- **An instance belongs to the database it was read from or written to.** `save()`, `refresh()` and `delete()` with no `db=` act on that database and table, whatever the class is bound to, on every model base, sync and async. Before, a row read with `Model.using(other_db)` was refreshed from, saved over and deleted in the database of its class: the same `_id` in another database, with no error. A successful `save(db=other)` moves the instance there; a write that fails leaves it where it was. `from_id(id, db=)` and `refresh(db=)` exist on every base. A copy (`copy.copy`, `copy.deepcopy`, `model_copy`) belongs where its original does; an unpickled instance belongs to its class's database. The database is no part of a comparison, a dump, `repr` or the stored document. Code that read a row from one database and relied on `save()` writing it to the class's database must now pass `db=`.
- **A `save()` of a row that is not there raises `NotFoundError`.** On the plain models (`SQLerModel`, the lite models, `AsyncSQLerModel`, `AsyncSQLerLiteModel`) and in `upsert_document(table, _id, doc)`, sync and async, a write by `_id` whose row is not in the database (deleted since it was read, or missing from the database given as `db=`) wrote nothing and returned as if it had saved, and `save(db=other)` moved the instance to `other`. It now raises `NotFoundError` naming the table and the id; the instance keeps its `_id`, its changes and its database. To copy a row into another database, save a new instance without the `_id`. Safe models still raise `StaleVersionError`.
- **`adapter.commit()` inside a transaction raises `TransactionStateError`.** Inside a `db.transaction()` block (a transaction opened by `begin_transaction`), sync and async, a raw `commit()` committed the rows written so far, so a transaction that then failed kept its first half. It now commits nothing and raises; the transaction goes on. `auto_commit()` stays the call that commits only outside a transaction.
- **Starting a transaction over raw work that is still uncommitted raises `TransactionStateError`.** `db.transaction()` / `begin_transaction()` after a raw `BEGIN`, or a raw write not committed yet, raises it naming `db.adapter.commit()` and `db.adapter.execute("ROLLBACK")`, sends nothing and leaves the work pending, sync and async. Before, sqlite3's `OperationalError` was raised, and the async adapter rolled the work back silently, so a `commit()` afterwards committed nothing.
- **A raw statement that ends a transaction raises `TransactionStateError` at that statement.** Inside a transaction, a raw `COMMIT`, `END` or `ROLLBACK` (any spelling), or a failure SQLite answers by rolling the whole transaction back (such as `ON CONFLICT ROLLBACK`), raises it with SQLite's error as the cause; every later statement in the transaction and the block's end raise the same error and send nothing. Before, the transaction went on unseen: a raw `ROLLBACK` lost the earlier rows and kept the later ones, and a block that raised after a raw `COMMIT` left its rows committed.
- **`insert_many`, `bulk_upsert` and their variants check the table's columns once per call.** A call of one row carries the check in its statement; a call of several rows sends it first, as one small `SELECT` in the call's transaction. A call costs about 3 µs more for one row and 9 to 16 µs more for a few; from a thousand rows on it is within 2% of before.
- **`AsyncSQLerDB.bulk_upsert` sends its rows as the sync method does**: inserts first, then updates, rows with the same keys in one statement. A document passed twice in one call makes two rows; before, the second was an update of the first.
- **`CacheAwareModel` names its cached results by the table its rows are written to.** `Meta.cache_table` still works, as a second name for the same results; the fallback to the class name in lower case is gone, so an entry tagged with that name is no longer dropped by a write. `cached_query`, `async_cached_query`, `QueryCache.set` and `invalidate_table` take a model class for `table=`. Table names are compared without regard to case, as SQLite compares them.
- **A write tells every `QueryCache`**, also one passed to the decorator as `cache=`; before, only the global cache was told. While a table is written inside an open transaction, `QueryCache.get` and `has` find no entry of it and `set` stores none.
- **Reading rows into pydantic models is about a third faster.** What kind a model class is (pydantic, lite or msgspec; frozen or not) is found once per class, not for every row and every attribute that is set. `all()` of 50,000 rows went from about 85,000 to about 115,000 rows a second on pydantic models, in memory and on a file, and is 4 to 6% faster on msgspec models; lite models read as fast as before.

### Removed

- **`PooledSQLerDB`, `PooledSQLiteAdapter`, `ConnectionPool` and the `sqler.pool` module**, with no alias. Use `SQLerDB`: it gives each thread its own connection and takes it back when the thread ends, so threads share one `SQLerDB` (`SQLerDB.on_disk(path)` in place of `PooledSQLerDB.on_disk(path, max_connections=n)`). There is no `max_connections`: the number of open connections is the number of live threads that used the database. `ConnectionPoolExhaustedError` stays; the async pool raises it.
- **`PoolStats` moved from `sqler.pool` to `sqler.adapter.asynchronous`** and is exported from `sqler`. Its fields are unchanged. A `PoolStats` pickled by an older version does not load.
- **`Transaction(adapter)` without a database.** `Transaction(adapter, db)` requires both; `db.transaction()` is the way to open one.
- **`TrackedModel.asave()`, `TrackedModel.afrom_id()` and `PartialUpdateMixin.asave_partial()`**, which called methods no model has. On an async model use `AsyncTrackedModel` and `AsyncPartialUpdateMixin`; `TrackedModel` on an async model raises `TypeError` when the class is defined.
- **`TrackedModel.from_id()`.** The model base's `from_id()` already returns a tracked, clean model.
- **`sqler.ResolutionError`, `sqler.CircularReferenceError`, `sqler.MaxDepthExceededError`, `sqler.MissingReferenceError` and its alias `sqler.MissingReferenceWarning`** (also from `sqler.exceptions`), **and from `sqler.utils`: `CircularReferenceError`, `ReferenceTracker`, `collect_references`, `ResolutionWarning`, `ResolutionResult`.** Nothing raised or returned them. Code that caught one can drop the handler: a cycle closes on its objects, a deep chain loads whole, and a reference to a row that is gone reads as `None` (left out of a list). The error to catch is the one a refused row raises, with its note.
- **`CacheAwareModel.asave()` and `adelete()`, and `SearchableMixin.asave()` and `adelete()`**, which called methods no model has. `await model.save()` and `await model.delete()` on an async model are the calls.

### Added

- **The async classes have every public name of their sync twins.** `AsyncSQLerModel` and `AsyncSQLerSafeModel` gain `is_dirty()`, `get_dirty_fields()`, `all()`, `first()` and `validate_references()`; `AsyncMigrationRunner` gains `reset()`; `AsyncSQLerQuery` can be imported from `sqler`.
- **`AsyncSQLiteAdapter.pool_stats()` and `AsyncSQLerDB.pool_stats()`** return `PoolStats`: pool size, free and in-use connections, checkouts, timeouts, average and longest wait.
- **`AsyncMigrationRunner.applied_migrations()`**, and `status()` returns `applied_count` and `applied` as the sync runner does.
- **`RebaseConfig.lock_timeout`** (seconds, default 5), and `LockTimeoutError` can be imported from `sqler`.
- **`SQLerDB.ensure_table()` and `AsyncSQLerDB.ensure_table()`** create a table with promoted columns, CHECK constraints and a version column (`table, *, promoted=None, checks=None, versioned=False`). They can be called again and add a missing version column to an existing table.
- **`AsyncSQLerDB.in_memory()` and `on_disk()` take `acquire_timeout`**, how long to wait for a free connection.
- **`AsyncAdapterABC.pool_stats()`** is part of the adapter interface; an adapter without a pool need not define it.
- **`docs/STORAGE.md`** describes how sqler lays out its tables on disk, for code that reads a database with plain SQL.
- **`Model.using(db, table)`** reads another table for one query without rebinding the class, on all model bases. The name is checked before any SQL. A row read this way saves, deletes and refreshes against the table it came from, and `as_ref()` names it. A copy of such a row made with `dataclasses.replace()` or `msgspec.structs.replace()` does not keep that table.
- **`FTSIndex(Model, fields, db=db)`** takes the database, for classes that were never bound.
- **`from_ids(ids, db=db)`** reads from a given database, on all model bases.
- **Every class call takes `db=`, so a class never bound with `set_db()` can do all a bound one does.** `add_index()`, `ensure_index()`, `validate_references()`, the soft-delete `active()`, `with_deleted()` and `only_deleted()`, `SearchableMixin`'s `search()`, `search_ranked()`, `search_count()`, `rebuild_search_index()` and `drop_search_index()`, and every import that takes a model class (`import_csv`, `import_json`, `import_jsonl`, their `_string` forms, `async_import_jsonl`) take `db=None`, keyword-only; given, the call works on that database only, also on a class bound to another. Queries go through `using(db)`. The `set_db()` and `bind()` warning and the `NotBoundError` of an unbound class say this rule.
- **`search(text, plain=True)`**, and the same on every search method of `FTSIndex` and `SearchableMixin`, finds the words of the text, so `C++`, `it's` and `foo-bar` can be searched. Without it the string is an FTS5 query, as before. `SearchQueryError` can be imported from `sqler`; it is a `QueryError`.
- **`AsyncTrackedModel` and `AsyncPartialUpdateMixin`**, exported from `sqler`: change tracking and `await model.save_partial(db=db)` for the async bases. `save_partial()` takes `db=` on the sync bases too.
- **`db.move_promoted(table, column, keep=...)`**, sync and async, and sqler's own table `_sqler_promoted`, which records the promoted columns that hold their values (`docs/STORAGE.md`). `_sqler_promoted` and `_sqler_migrations` are refused as table names (`sqler.utils.SQLER_TABLES`), and `get_stats()` / `async_get_stats()` no longer count them as tables.
- **`AsyncSQLerQuery.iter_dicts()` and `AsyncSQLerQuerySet.iter()`** give rows one at a time with `async for`, as the sync `iter_dicts()` and `iter()` do. Outside a transaction the iteration holds one pooled connection until it ends, and gives it back however it ends (its rows run out, `aclose()`, the iterator is dropped, an exception, a cancellation), whichever task ends it. A loop that saves each row gets each row once, as the statement saw it.
